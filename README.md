# Music Analytics

Conversational analytics over the [MusicBrainz](https://musicbrainz.org/doc/MusicBrainz_Database/) music metadata
database. Natural-language questions are answered by an LLM agent that reasons over an
[Apache Ossie](https://ossie.apache.org/) semantic layer (datasets, metrics, relationships) instead of raw SQL
tables, then executes read-only queries against a local Postgres copy of MusicBrainz.

Text/insight answers only for now — generative BI visualization is a planned second phase.

## Setup

### 1. Install Python dependencies

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

### 2. Bring up the MusicBrainz database

```bash
cp .env.example .env   # then edit .env with real credentials
./scripts/setup_musicbrainz_db.sh
```

This clones `musicbrainz-server` (for its official importer), downloads the MusicBrainz **sample** dataset
(small, meant for development — not the full biweekly snapshot), and imports it into a local Postgres database.
See the script for how to swap in a full dump later.

Then lock down query access for the agent:

```bash
psql -f scripts/create_readonly_role.sql
```

### 3. Generate the semantic layer for everything else

`semantic/core/` hand-curates the entities that matter most for analytics. Everything else in the
~180-table MusicBrainz schema is auto-generated by reflecting the live database:

```bash
python -m semantic.generator.introspect generate
```

This writes one `*.ossie.yaml` per table not already covered by `semantic/core/` into `semantic/generated/`
(gitignored — regenerate on demand rather than committing it).

### 4. Run the chat loop

```bash
python -m agent.chat
```

Defaults to `claude-sonnet-5`. Override with `--model` (e.g. `--model claude-haiku-4-5-20251001` for
cheaper/faster, `--model claude-opus-5` for tougher questions) — without an explicit model the underlying
SDK falls back to whatever your `claude` CLI is configured to account-wide, which can be an expensive
model for what is a narrow, mechanical tool-calling workload.

## Running tests

```bash
pip install -e ".[dev]"
python -m pytest
```

`tests/test_semantic_models.py` validates every hand-authored `semantic/core/*.ossie.yaml` file against the
real Ossie Pydantic models. `tests/test_introspect.py` is an integration test for the auto-generation tool —
it exercises real Postgres reflection (column types, foreign keys) rather than mocking it, so it needs a
database it's allowed to create schemas in. One-time setup:

```bash
sudo -u postgres psql -c "ALTER ROLE $(whoami) CREATEDB CREATEROLE;"
psql -U $(whoami) -d postgres -c "CREATE DATABASE music_analytics_test;"
```

The test creates and drops its own schema inside `music_analytics_test` on each run, so it doesn't touch
the real `musicbrainz` database.

## Project layout

- `semantic/core/` — hand-authored Ossie YAML models for the core entities (artist, release, recording, work,
  label).
- `semantic/generator/` — introspects the live Postgres schema and auto-generates Ossie YAML for tables not
  covered by `core/`.
- `agent/` — the semantic catalog loader, SQL builder, agent tool definitions, and the CLI chat entrypoint.
- `scripts/` — one-time database setup (importer + read-only role).
